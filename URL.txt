The process of fetching data from a URL and turning it into slide content is handled by a pipeline that combines Web Scraping, Vector Search (RAG), and Multi-Agent LLM Logic.

Here is the step-by-step breakdown:

1. Data Fetching (The "Loading" Phase)
When you provide a URL, the system uses the `load_document` function in document_loader.py:
- WebBaseLoader: It uses LangChain's `WebBaseLoader` to request the URL and extract the visible text from the HTML.
- Cleanup: It automatically strips excessive whitespace and formatting to ensure the AI receives "clean" text, reducing token waste.

2. RAG Ingestion (The "Brain" Phase)
Before the AI writes any slides, the fetched text is processed in rag_engine.py to make it searchable:
- Chunking: The long text from the website is broken into small "chunks" (1,000 characters each). This is important because LLMs have a limit on how much text they can "read" at once.
- Embedding: Each chunk is converted into a mathematical vector (a list of numbers) using the `all-MiniLM-L6-v2` model.
- FAISS Index: These vectors are stored in a FAISS (Facebook AI Similarity Search) database. This allows the system to find the exact paragraph needed for a specific slide title in milliseconds.

3. Slide Content Generation (The "Writing" Phase)
This is where the agents in agent_graph.py take over:

- Step A: The Planner:
    - The `planner_node` queries the FAISS index for a "General Summary" of the website.
    - It uses this summary to create a logical Outline (e.g., Slide 1: Introduction, Slide 2: Key Features, etc.).

- Step B: The Content Writer (Similarity Search):
    - For every single slide in the outline, the `content_node` goes back to the FAISS index.
    - If the slide title is "Market Trends," it searches the index for "Market Trends" and retrieves the top 2-3 most relevant paragraphs from your URL.
    - The Prompt: It sends these specific paragraphs to Gemini with a strict instruction: "Use ONLY this retrieved context to write the slide content. Do not hallucinate."

- Step C: The Refiner:
    - If Gemini writes too much text (which might overflow the slide), the `refine_node` detects the length and asks the AI to rewrite it more concisely while keeping the facts from the URL.

Summary Flow:
1. URL -> WebBaseLoader -> Raw Text.
2. Raw Text -> Chunks -> Vectors -> FAISS Store.
3. Slide Title -> Vector Search -> Relevant Context.
4. Context + Gemini -> Final Slide Content.

This approach ensures that your slides aren't just generic AI guesses, but are actually grounded in the specific data found at the URL you provided.






For the PPT generation in this project, we used a Hybrid Multi-Agent & Programmatic Approach. This design was chosen to ensure a balance between AI creativity (Gemini) and structural reliability (Python).

Here is a breakdown of the approach and the reasoning behind it:

1. The Approach: Multi-Agent Orchestration + Programmatic Rendering
The generation process is split into two distinct phases:

Phase A: Intelligent Content Synthesis (The Agent Graph)
Using LangGraph and Gemini 2.5 Flash, we orchestrate a team of specialized agents:

Planner: Creates a logical narrative flow (The Outline).
Designer: Analyzes the topic/tone to pick a custom color palette and font pairing (The Theme).
Writer: Fills the slides with granular detail, using RAG (Retrieval-Augmented Generation) to ground the content in your uploaded PDFs or URLs.
Refiner: A "critic" agent that detects if a slide is too wordy and proactively shortens it before the file is even created.
Phase B: Professional Rendering (

ppt_utils.py
)
The output from the AI is a structured JSON, which is then fed into the python-pptx library. This layer handles:

Smart Pagination: If the content is still too long after AI refinement, the code automatically splits it into "Continuation" slides.
Dynamic Theming: Applies the AI-generated HEX codes and fonts to shapes, backgrounds, and text.
Parallel Image Fetching: Uses ThreadPoolExecutor to fetch and embed relevant images for every slide simultaneously.
2. Why we used this particular approach?
We avoided a simple "one-shot" AI prompt for several key reasons:

Reliability & Readability: Pure AI outputs are unpredictable. Programmatically calculating text height and wrapping ensures that text never overflows the slide or covers the footer, which is a common failure in simpler AI PPT generators.
"Premium" Design Feel: By having a dedicated Designer agent, the PPT isn't just a generic template. A presentation on "Ocean Biology" gets a different color scheme (blues/teals) than one on "Cybersecurity" (dark grays/greens), making it feel custom-made.
Accuracy (RAG integration): Most AI PPT tools rely on internal knowledge. By using a graph with a RAG step, we ensure the slide content is actually based on the precise documents you provide, significantly reducing hallucinations.
Performance: Handling image fetching and file assembly in Python is significantly faster and more stable than asking an LLM to generate raw XML or Base64 data for a PowerPoint file.
This hybrid model gives you the intelligence of an AI for the content and the precision of a software engineer for the final presentation layout.
